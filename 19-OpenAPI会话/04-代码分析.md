# 代码分析

分析分支：`vtron_java_server` `dev`。2026-09-23 `git pull` 已是最新。

验签、请求头和 HMAC 在上面。Bearer 会话和商户站 Token 在最后一节。

对照文档 `docs/virtronex/OpenAPI-签名规范.md`。下面和文档不一致的地方以代码为准。

## 拦哪些请求

`virtronex-api/.../web/filter/OpenApiSignatureFilter.java`。`shouldNotFilter`：路径不是 `/api/v1` 开头就不进。渠道回调在 `virtronex-callback`，不走这个 Filter。

进门后文案语言固定成 `Locale.US`。

过滤器读四个头：`X-App-Id`、`X-Timestamp`、`X-Nonce`、`X-Sign`。`Content-Type` 以 `multipart/` 开头时，参与签名的 body 当成空串。其它请求用原始 body 字符串。验签在解密之前。

## 验签顺序

落点：`OpenApiAuthService.verifyAndGetIdentity`。顺序是 appId、时间戳、nonce、签名。失败都是业务码 `30005`，HTTP 200，避免客户端把验签失败当成登出。文案键在 `messages.properties`。

1. `X-App-Id` 空：`api.missing.app.id`。英语是 “Application credentials are missing. Please try again later.” Android 第一包空 app id 时界面上就是这句。
2. 用 app id 查 Redis 凭证 `ResellerApiCacheSupport`。没有或已停用：`api.invalid.app`。
3. `X-Timestamp` 按秒解析。空或不是整数：`verify.sign.error`。和当前时间相差超过 `reseller.api.timestamp.tolerance-seconds`，默认 300 秒：`api.timestamp.expired`。文档写的是毫秒会失败，代码确实按秒比。
4. `X-Nonce` 空：`api.missing.nonce`。否则 `OpenApiSessionService.trySetNonce`，Redis 键是 `reseller_api:nonce:` 拼上 nonce 本身，不含 app id。`setIfAbsent`，TTL 是 `reseller.api.nonce.expire-seconds`，默认 300 秒。占不上：`api.nonce.reused`。文档写成「同一个 appId 在 300 秒内不可重用」。代码是全局 nonce，换一个 app id 再用同一个 nonce 也会被拒。
5. 缓存里的 secret 先 `ResellerApiAppSecretCodec.decryptForHmac`，再算期望签名。对不上：`api.sign.mismatch`。`X-Sign` 空也走这一支，没有单独的缺签名键。比较前两边都转小写，用 `MessageDigest.isEqual`。

nonce 在比对签名之前就写入 Redis。签名错了，这个 nonce 在 TTL 里也不能再用。

## HMAC

`OpenApiAuthService.buildSign`。

待签串是 `appId + timestamp + nonce + canonicalBody`，直接拼接，没有分隔符。`X-Sign` 是 HMAC-SHA256 的十六进制小写。

`canonicalBody` 是 `PlatformCanonicalJson.normalizeBodyForSigning`：能解析成 JSON 时，对象键按字典序，数组顺序保留，再压成紧凑字符串。解析失败就用原始字符串，不因此拒绝。空 body 是空串。multipart 在过滤器里已经换成空串，所以待签串只到 nonce 为止。

加密默认开着，并且 `openapi.crypto.required` 默认 true。这时客户端签的是 envelope 密文 JSON，不是业务明文。验签通过后，过滤器再用该 app id 的请求私钥解密。body 有内容却不是 envelope：`30023` `aes.decrypt.error`，同样是 HTTP 200。没有私钥且 required 为 true，也是 `30023`。multipart 不解密。

## 验签之后还要哪些头

登录前路径也要客户端上下文，不只登录这一条。`OpenApiClientContextResolver.requireClientContext`：

- `X-Device-Id` trim 后长度 8 到 128。没有字符集检查。不合格：HTTP 400，业务码 `10010`，文案键 `api.device.id.invalid`。
- `X-Client-Platform` 显式值只接受 `web`、`h5`、`android`、`ios`，大小写不敏感。非法值：`api.client.platform.invalid`。没传时用 `User-Agent` 推断，推断不出：`api.client.platform.required`。这两种也是 HTTP 400、`10010`。

文档把注册、忘记密码、未登录发码写成「只要签名、不要这两个头」。代码里这些路径在 `isPreLoginAuthPath` 里，一样要设备头。这个名单上的 POST 不要求 Bearer：

- `auth/login`、`auth/google/login`、`auth/google/linkWithPassword`、`auth/google/register`
- `auth/apple/login`、`auth/apple/linkWithPassword`、`auth/apple/register`
- `auth/check/password`、`auth/check/emailExists`
- `email/send`、`email/verify`
- `app/version`
- `customer/register`、`customer/bankFunction`、`customer/forgetPassword`
- `qr/resolve`

文档第六节的「仅验签」名单更短，没有 `check/password`、`check/emailExists`、Google、Apple 和 `qr/resolve`。以过滤器这份名单为准。

`POST /api/v1/auth/logout` 在验签之后、设备头之前单独处理。有 Bearer 就删会话，没有 Bearer 也放行。这一支不调用 `requireClientContext`，所以不强制 `X-Client-Platform` 和 `X-Device-Id`。删会话的细节在下一节。

其余 `/api/v1/**` 在验签和设备头之后还要 Bearer。

## 会话和商户站 Token

C 端拿到的登录 token 不是 JWT。`OpenApiSessionService.createSession` 用去掉横线的 UUID。认不认，只看 Redis。

两把键：

- 会话体 `reseller_api:session:` 加 token。字段有 `merchantId`、`resellerId`、`resellerApiId`、`appId`、`loginTime`、`clientPlatform`、`deviceId`。
- 活跃指针 `reseller_api:active:` 加 `merchantId`，值是当前这一个 token。同一商户只有一把指针，不再按 web / mobile 分桶。

TTL 默认 `reseller.api.session.timeout-seconds`，432000 秒，也就是 5 天。读会话成功时两把键都按这个时长重新计，不是只消耗剩余时间。

谁发会话：`AuthController.login`，以及 `isComprehensiveKyc = 1` 时 `MerchantApiController` 的注册。Google、Apple 登录也调 `createSession`，身份怎么验归 `04-第三方登录`。会话里的 `resellerId` 用商户自己的，不用平台凭证签名上的 0。

`createSession` 先踢掉这个商户已有的 OpenAPI 会话，再踢商户站。商户站的签发类注释指向 `MerchantLoginSessionSupport`，这个仓库里没有这个类。能看到的只有互踢时动的键：`merchant:login:session:{merchantId}` 里存的 access token 被删掉，同时删 `token:`、`merchant:login:auth_token:`、`auth_token:` 三条白名单，并写 `merchant:login:crowd_out:` 和 `crowd:out:member:`，TTL 至少 7 天。商户站新登录时会反过来删 OpenAPI 的指针和会话体。两边不能同时在线。

带 Bearer 的请求走 `getAndRefreshSession`。下面任一情况都返回空，过滤器一律 HTTP 401，body 里 `code` 为 `401`，文案键 `api.token.required`。英语是 “Login required or token is invalid”。没有单独的业务码区分过期、换设备和被顶号。

- 没有 Bearer，或会话体不存在
- 会话里缺平台或设备
- 当次 `X-Client-Platform`、`X-Device-Id` 和会话里存的不一致。设备号按原字符串比，不忽略大小写
- 活跃指针不是这枚 token。被新登录顶掉之后，旧 token 即使会话体还在也会被拒

平台凭证（`reseller_api.id` 在 `reseller.api.platform-ids` 里）跳过「签名 reseller 和会话 reseller 必须相同」。BU 凭证对不上仍是上面的 401。过滤器放行后，身份里的 `merchantId`、`resellerId`、`resellerApiId` 用会话里的，`appId` 仍用这次签名的。

`removeSession` 不核对平台和设备。删会话体；活跃指针如果还指向这枚 token 也删。能读出 `merchantId` 时，把该商户的推送绑定软失效。没有 Bearer 的 logout 不会进这个方法。

## 后台密钥接口

`02-用户视角` 里的缺 app id 和 HTTP 401 已经落在上面。`-1002`、`-1003` 是 Android `OpenApiInterceptor` 在本机造的，没有对应服务端接口。

`03-管理后台` 里的四个接口在 `virtronex-manage` 的 `ResellerController`，前缀 `/reseller`。都要求平台员工。

- `POST /reseller/api-key/list` → `apiKeyList` → `ResellerApiBuServiceImpl.list`。按 `resellerId` 列 `reseller_api`，不返回 secret。
- `POST /reseller/api-key/add` → `apiKeyAdd` → `create`。先过操作员邮箱码，类型 `platformApiKey`；开了验证器还要谷歌码。然后写入密钥并 `refreshByAppId`。
- `POST /reseller/api-key/update` → `apiKeyUpdate` → `update`。同样要验证码。改名称、回调、联系人、备注和状态，再刷新这一条缓存。状态不是 1 或停用值时直接拒绝。
- `POST /reseller/api-cache/reload` → `reloadApiCache`。权限另是 `bu:reseller:reloadApiCache`。`resellerApiCacheSupport.reloadAllFromDb`，返回 `reloaded` 和 `removedStale`。

新建和修改发码是 `POST /email/sendCheckEmailWithoutEmail`，`EmailController.sendCheckEmailWithoutEmail` → `PlatformEmailSendService.sendCheckEmailWithoutEmail`。信发给当前登录员工，不发给密钥上的联系邮箱。模板归 `27-邮件与告警`。
