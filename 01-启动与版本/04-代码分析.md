## 登录页上没有更新框

`POST /api/v1/app/version`。`AppVersionApiController.getVersion`。

`virtronex/virtronex-api/src/main/java/com/virtronex/api/web/controller/appVersion/AppVersionApiController.java`

登录页和首页创建时调用。登录前路径，不要求 Bearer。app id 从验签放进的 `OpenApiAuthenticationToken` 取，不从 body 取。取不到就当空字符串。

body 可以没有。`type` 只 `trim`，不改大小写，也不校验必须是 `android` 或 `ios`。空则按空字符串去等值匹配 `app_version.type`。`version_code` 别名 `versionCode`。`null`、小于 1 都当成没传。

这一屏不传 `version_code`，走 `AppVersionClientQuerySupport.findForClient` 里的 `findLatest`。

`virtronex/virtronex-api/src/main/java/com/virtronex/service/service/support/AppVersionClientQuerySupport.java`

表 `app_version`。没有状态列。按 `create_time` 降序，再按 `id` 降序，取一条。不比较 `version_code` 谁更大。

1. 签名 app id 加上 `type` 有行，就用这一行。
2. 没有，再找 `reseller_api` 里 `reseller_id = 0` 且 `status = 1`，`ORDER BY id ASC LIMIT 1` 的 `app_id`。和验签白名单 `reseller.api.platform-ids` 不是同一套。测试库这条是 `reseller_api.id = 1`，不是 id 5 的 android-tst。
3. 还没有，再用 `type` 相同、`app_id` 为空串或 NULL 的历史行。

测试库用 android-tst、`type=android`、不传 `version_code`，落到 `app_version.id = 16`，`update_type = 1`，`version_code = 114`，`version_name = 1.1.3`。

旁边的名字：响应 `updateType` 是这一行的 `update_type`，0 强制，1 非强制。服务端不用它和本机版本比。框出不出现是客户端拿响应 `versionCode` 和本机 118 比。平时 114 不大于 118，所以 `update_type` 已经是 1 也不弹。

传了 `version_code` 且大于等于 1 才走 `findExact`：只等值匹配 `app_id + type + version_code`。先签名 app id，没有再走平台 app id。不回退最新行，也不走空 `app_id`。查无则成功码 `200`，`data` 为 null。这一屏没走这条。

同库 `type=ios` 最新是 id 33，`update_type = 0`。iOS 登录页要返回的 `versionCode` 达到 118 才露出 Apple，见 `04-第三方登录/02-Apple登录/02-用户视角`。不是 Android 这一屏。

响应 `AppVersionClientVo.from` 不返回兼容列 `version`。字段是 `id`、`type`、`url`、`updateType`、`versionCode`、`versionName`、`updateContent`、`createTime`、`googleSignIn`、`appleSignIn`。

`googleSignIn`、`appleSignIn` 只有 1 是开，null 和其它值都变成 0。这一屏的更新框不看它们。登录归 `04-第三方登录`。

```text
注解：`virtronex/virtronex-api/.../AuthController` 的登录
不读 `app_version`，也不读 `updateType`。服务端登录不会因为强制更新拒绝。挡住登录页的是客户端盖上来的框。
```

## 菜单「APP版本」列「更新方式」

`POST /settings/appVersion/current`。`SettingsController.appVersionCurrent`。`SettingsBuServiceImpl.selectCurrentAppVersions`。

`virtronex-manage/virtronex-main/src/main/java/com/virtronex/web/controller/settings/SettingsController.java`

`virtronex-manage/virtronex-system/src/main/java/com/virtronex/system/service/impl/SettingsBuServiceImpl.java`

每个 `app_id + type` 按 `create_time`、`id` 取最新一行，和 C 端 `findLatest` 的排序一样。列「更新方式」读 `update_type`：0 显示强制更新，其它显示非强制。

平台员工不按 reseller 过滤。BU 账号只看自己 reseller 下、`status = 1` 的密钥所挂的 `app_id`。权限 `bu:settings:appVersion:list`。

更新记录 `POST /settings/appVersion/page`，`selectAppVersionPage`。详情里更新方式只是标签，不能改旧行的 `update_type`。`Save` 走下面的 `updateSignIn`。

## “Add” 再插一行

`POST /settings/appVersion/add`。`SettingsBuServiceImpl.addAppVersion`。只 `INSERT`，`create_time` 用 `NOW()`。编辑不改原来那一行。权限 `bu:settings:appVersion:edit`。

`update_type` 原样写入。页面只发 0 或 1，默认 1。`version` 和 `version_name` 都写成提交的版本名称。App ID 必须是启用中的 `reseller_api.app_id`。

没有缓存。C 端下一次不带 `version_code` 的查询会拿到这行，如果它成了该 app id、该 type 下最新的。Android 还要这行的 `version_code` 大于本机才弹框。

`AppVersionFieldSupport.requireForCreate` 注释指向另一处 `POST /appVersion/add`。这一页走的是 `/settings/appVersion/add`，没有调用那个方法。
