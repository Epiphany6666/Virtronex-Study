# 代码分析

分析分支：`vtron_java_server` `dev`。2026-09-23 `git pull` 已是最新。公共签名见 `19-OpenAPI会话`。`02`、`03` 里多出来的接口见文末对账。

第 1 次写 `login`、`linkWithPassword`、`register`。第 2 次写 `bind`、`unbind`。登录页见 `02-用户视角`。

三个都在 `AppleSignInController`，前缀 `/api/v1/auth/apple`。只要签名，不要 Bearer。签名上下文没有 reseller 是 `30005`，文案键 `api.invalid.context`，英文 “Invalid request. Please try again later.”。

灰度开关在验 `identity_token` 之前。`AppleOAuthLoginFacade.assertLoginEnabled`，Nacos `apple.signin.login-enabled`。代码里默认 `false`。关掉是 `40205` `apple.login.disabled`，英文 “Apple sign-in is not available.”。

`identity_token` 由 `AppleSignInBindSupport.requireIdentity` 验。验不过是 `40200` `apple.identity.invalid`，英文 “Apple sign-in could not be verified. Please sign in with Apple again.”。令牌里的邮箱可以没有。

登录和连密码走 `OpenApiPreLoginCommitScene.LOGIN` 那档限流。注册走 `REGISTER`，再加 `checkBeforeRegister`，成功后 `recordRegisterSuccess`。限流键优先用令牌里的邮箱，没有就用 `apple:` 加 `sub`。数字见 `02-邮箱注册登录`。

成功都走 `ComprehensiveKycSupport.sessionPayload`：`token`、`expires_in`、`merchant_id`；只有综合 KYC 才再加 `binConfigId`。`bankFunctionEnabled` 不在这次响应里。会话按商户自己的 `reseller_id` 建，不用签名上的。同商户互踢。`merchant_login_log.login_method` 是 `apple`，`login_email` 记的是令牌里的邮箱，没有就是空。

这三支的代码里没有银行开户查询。

|------|------|----------|----|
| `merchant_apple_bind` 已绑定，商户 `status = 1` | `login` | 发会话。刷新 `last_login_at`。令牌里有邮箱才改 `apple_email`，有昵称才改显示名。不改 `merchant.email` | 用户 |

| 这个 `sub` 没绑定，令牌没有邮箱，或邮箱没有账号 | `login` | 不变。`40206` | 用户 |

| 已登录，当前有绑定 | `unbind` 二次因子过 | `status = 0`，`deleted` 写成这行 id，写解绑历史 | 用户 |

## 登录

`POST /api/v1/auth/apple/login`。`AppleSignInController.login` → `AppleOAuthLoginFacade.login`。

按 `apple_sub` 查 `merchant_apple_bind`。没有行时：令牌没有邮箱，直接 `40206` `apple.register.required`，英文 “Please set a password to create your account.”。有邮箱再查 `username` 或 `email`。对得上平台账号是 `40204` `apple.email.already.registered`，英文 “This email is already registered. Sign in with your password to link Apple.”。`data.googleEnabled` 表示这个商户的验证器是否开着（`google_verify.type = 2` 且 `google_status = 1`）。`data.appleEmail` 是这次用来对账号的邮箱。对不上也是 `40206`。这一步不建号。

有绑定行但商户行没了，对外是 `40203` `apple.not.bound`，英文 “No Apple account link was found.”。

不是平台凭证时，商户 `reseller_id` 必须等于签名上的。否则 `40202` `apple.sub.bound.elsewhere`，英文 “This Apple ID is already linked to another account.”。`status` 不是 `1`：码是 `20007`，文案键 `user.disabled`，和邮箱登录同一句。敏感邮箱拦截走 `MerchantSensitiveEmailBlockSupport`。

不验邮箱码，也不验动态码。登录日志 `second_factor` 为空。

会话发出之后 `touchAppleProfile` 只改绑定行。令牌没有邮箱就不改 `apple_email`，没有昵称就不改显示名。失败吞掉，不把已经发出的会话打成失败。`merchant` 的 `email`、`username`、`real_name` 不动。

## 连密码

`POST /api/v1/auth/apple/linkWithPassword`。`linkWithPassword`。给 `login` 返回 `40204` 之后用。

密码空是 `10010`，文案键 `api.username.password.required`，英文 “Username and password are required.”。平台邮箱先用令牌里的，没有再用 body 的 `email`（去空格、转小写）。两边都没有是 `40207` `apple.email.required`，英文 “Email is required to continue with Apple.”。按这个邮箱找商户，没有是 `40203`，不是 `40206`。跨 BU、停用、敏感邮箱和登录同一套。这个 `sub` 已经绑在别的商户上是 `40202`。

密码走 `MerchantLoginPasswordAttemptService.verify`。输错、锁定见 `02-邮箱注册登录`。

二次因子在 `OpenApiPasswordLoginMfaSupport.matchForAppleLink`。验证器开着必须带 `googleCode`，只带邮箱码是 `40014` `google.code.required`，英文 “Google Authenticator code is required.”。没开却带了动态码是 `40028` `google.not.on`，英文 “Google authentication is not enabled.”。没开则要邮箱码，键 `merchant:apple:signin:link:email:code`，发码 `type` 为 `linkAppleSignIn`。位数和输错见 `03-验证码与登录加固`。两头都空是 `20003` `code.invalid`。

通过后先占住这道校验，再 `AppleSignInBindSupport.bind`，`operator_type` 是商户自己。写入失败会把码放回。本账号已经绑了另一个 `sub` 是 `40201` `apple.already.bound.other`，英文 “This account is already linked to another Apple ID. Unlink it first.”。同一个 `sub` 再绑一次只刷新资料，不再写一条历史。没有有效行就插入；有解绑过的行就改活那一行。令牌没有邮箱时，改活那一行不会把已有 `apple_email` 写成空。插入的列是 `apple_sub`、`apple_email`、`display_name`、`bound_at`、`reseller_id`、`status` 为已绑定、`deleted` 为有效。头像写成空。历史在 `merchant_apple_bind_log`：这名商户还没有任何历史是 `bind`，已经有过是 `rebind`。成功才发会话，然后再 `touchAppleProfile`。`second_factor` 记实际用的：`google_2fa` 或 `email_otp`。不改 `merchant` 的邮箱三列。

## 注册

`POST /api/v1/auth/apple/register`。`register` → `MerchantRegisterService.registerViaApple`。给 `40206` 之后用。免邮箱码。

平台邮箱的取法和连密码相同，没有是 `40207`。`sub` 已经有绑定是 `40202`。邮箱或用户名已存在是 `40204`，同样带 `googleEnabled` 和 `appleEmail`。

密码必须匹配 `^(?=.*\d)(?=.*[a-z])(?=.*[A-Z]).{8,20}$`，否则 `40009` `password.set.error`，英文 “Must be 8–20 characters with numbers, uppercase, and lowercase letters.”。空密码是 `10010` `param.empty.error`，英文 “Please fill in all required fields to continue.”。

邀请码和邮箱注册同一套：`agentInviteCode` 优先于 `inviteCode`，没传或没命中回退 BU 默认码，再没有用 Nacos。平台凭证全库查，BU 凭证只查该 BU。见 `02-邮箱注册登录`。差别是 BU 凭证下，解析出来的 `reseller_id` 必须等于签名 BU，含回退默认码。对不上是 `20010` `invite.code.invalid`，英文 “Invalid invite code. Please check and try again.”。

然后 BCrypt，`initMerchantByEmail`，`register_via = apple`。钱包和加点与邮箱注册相同，见 `02`。事务提交后 `scheduleCreateDepositAddressesAfterCommit`。是不是和邮箱注册同一段建地址，归本子项 `06`。

建号成功后 `bind`，`operator_type` 是系统，不是商户自己点的连接。再发会话。不验动态码，`second_factor` 为空。敏感邮箱在建号前拦一次，建号后再拦一次。

## 绑定

`POST /api/v1/auth/apple/bind`。`AppleSignInController.bind` → `AppleSignInBindSupport.bindWithSecondFactor`。要登录态。没有会话是 `20008` `token.error`，英文 “Session expired. Please log in again.”。商户行没有是 `20006` `member.not.found`，英文 “Account does not exist.”。

不看灰度开关。商户 `status`、KYC、银行开户都不读。`identity_token` 仍要验过，不过是 `40200`。

二次因子在 `MerchantSecondFactorAuthSupport.matchGoogleElseEmailWithoutConsume`。验证器开着必须带 `googleCode`，不会改去验邮箱。码空是 `10015` `google.code.empty.error`，英文 “Google authentication code is required.”。对不上是 `10012` `google.code.incorrect`，英文 “Incorrect authenticator code.”。没开才验邮箱码，键 `merchant:apple:signin:bind:email:code`，发码 `type` 为 `bindAppleSignIn`。邮箱码空、过期或对不上是 `20003`。位数和输错见 `03-验证码与登录加固`。没开时就算 body 里带了动态码，也不走 `40028`，只验邮箱。

邮箱码在写入前删掉，写入抛错会放回。动态码不占住这一步，同一窗可以再用。对上之后会改 `google_verify.last_verify_time`。算法见 `06-谷歌验证器`。

然后 `doBind`。本账号已经绑了另一个 `sub` 是 `40201` `apple.already.bound.other`，英文 “This account is already linked to another Apple ID. Unlink it first.”。这个 `sub` 绑在别的商户上是 `40202`。同一个 `sub` 再绑一次只刷新资料，不再写历史。令牌没有邮箱就不改已有 `apple_email`。没有有效行就插入；有解绑过的行就改活那一行。写入的列和第 1 次连密码相同。`operator_type` 是 `merchant`。

历史在 `merchant_apple_bind_log`。这名商户还没有任何历史是 `bind`，已经有过是 `rebind`。记下 `apple_sub`、`apple_email`、操作者和 IP。昵称不进这张表。不改 `merchant` 的邮箱三列，也不发新会话。成功 data 为空。

## 解绑

`POST /api/v1/auth/apple/unbind`。`unbind`。登录态和绑定一样。也不看灰度开关，不读 `status` 和 KYC。这一步不要 `identity_token`。

先看当前有没有有效绑定。没有是 `40203`，这时还没验二次因子。

有绑定才验，和绑定同一套：验证器开着必须动态码，空是 `10015`，错是 `10012`，不接受邮箱码顶上。没开才用邮箱码，键 `merchant:apple:signin:unbind:email:code`，发码 `type` 为 `unbindAppleSignIn`。空或对不上是 `20003`。

通过后 `softUnbindById`：`status` 写成 `0`，`deleted` 写成这行的 id，昵称和头像清空。`apple_sub`、`apple_email` 留在这行上，但查询只认 `deleted = 0`，所以登录按 `sub` 会当成没绑定。行不物理删除。并发下已经解绑过，仍是 `40203`，邮箱码会放回。

历史记一条 `unbind`，`operator_type` 是 `merchant`。不改登录密码。解绑后邮箱加密码仍能登录。后台强制解绑见文末对账。

## 对账

`02-用户视角` 没有打出新的卡平台接口。Android 登录页没有 Apple 按钮，没有发出上面的 `POST /api/v1/auth/apple/login`。Account 里的第三方页这次没进，布局里也只有 Google。H5、Web 没有 Apple 登录页。iOS 源码里的登录、连密码、注册、绑定、解绑就是上面几节，这次没跑。按钮显不显示看 `/api/v1/app/version` 且 `type=ios` 的 `versionCode` 是否大于等于 `118`，版本检查归 `01-启动与版本`。

`03-管理后台` 多出列表、详情、历史和强制解绑。重置验证器归 `06-谷歌验证器`。

`POST /security/appleBinding/page`。`MerchantAppleBindingController.page`。权限 `bu:appleBinding:list` 或 `main:appleBinding:list`。主表是 `merchant`，左连 `merchant_apple_bind`，只连 `deleted = 0`。没有有效绑定行，状态就是 `unbound`，所以 `100985` 没有绑定行也会出现。按商户 id 倒序。这次没筛时 927 行；Bind status 选 Bound 后 2 行，是 `100839` 和 `100527`。

`POST /security/appleBinding/detail`。权限 `bu:appleBinding:query` 或 `main:appleBinding:query`。商户 id 空、不在数据范围、或商户行没有，都是 `record.notFound`，英文 “Record not found or operation not permitted.”。不区分「没有这个人」和「不归你」。`100985` 打开后 Registration Method 是 Email，Account Status 是 Normal，Status 是 Unbound，Apple Binding 一栏是 “Not connected to Apple Sign-In.”。

`POST /security/appleBinding/logPage`。权限和详情相同。先确认商户在范围内，再读 `merchant_apple_bind_log`，按 `create_time`、`id` 倒序。`100985` 没有历史，表是 No Data。

`POST /email/sendCheckEmailWithoutEmail`。`EmailController.sendCheckEmailWithoutEmail`，要已登录。弹窗 `Get code` 的 `type` 是 `platformForceUnbindMerchantApple`。码发到当前员工邮箱，Redis 键 `platform:reset:merchant:apple:force:unbind:email:code`。不改 `merchant_apple_bind`。邮件模板归 `27-邮件与告警`。重置验证器、强制解绑 Google 也走这个路径，`type` 不是这一个，不在这篇。这次没有点 `Get code`。

`POST /security/appleBinding/forceUnbind`。权限 `bu:appleBinding:forceUnbind` 或 `main:appleBinding:forceUnbind`。服务 `MerchantAppleBindingServiceImpl.forceUnbind`。商户、邮箱码、原因缺一个，或原因去空格后为空、长于 255，是 `merchantAppleForceUnbind.param.required`，英文 “Required parameters are missing.”。不在范围是 `record.notFound`。没有仍生效的绑定，或解绑时刚好被别人先解掉，是 `apple.not.bound`，英文 “No Apple account link was found.”，不再写一条日志。邮箱码先对员工那把键。员工开了验证器才要谷歌码，空着是 `google.code.required`，英文 “Google authentication code is required.”，不对是 `google.code.invalid`，英文 “Incorrect Google verification code.”；没开就跳过，和这次弹窗没有谷歌码一致。通过后 `softUnbindByMerchantId`：`status` 写成 `0`，`deleted` 写成这行 id，显示名和头像清空。`apple_sub`、`apple_email` 留在行上，查询只认 `deleted = 0`。再往 `merchant_apple_bind_log` 插一行，`event_type = unbind`，`operator_type = admin`，带原因、操作者、IP。不踢商户在线会话。这次点了 `Cancel`，没有看到 “Apple Sign-In unbound”。库里 `100839` 和 `100527` 的 `status` 仍是 `1`，`deleted` 仍是 `0`。弹窗英文警告写成 Google，那是前端文案，接口仍解的是 Apple 绑定。
