## 提交

`POST /api/v1/KYC/submit`

落点：`MerchantKycApiController.submit` → `MerchantKycSubmitFacade.submitNew` → `MerchantKycServiceImpl.commitInfo`。

要登录态。没有商户：`20008`，文案键 `api.token.required`。商户行不存在：`MEMBER_NOT`。请求体空：`10010`，文案键 `param.empty.error`。`binConfigId` 空：`BIN_CONFIG_ID_REQUIRED`。没有 `binConfigId` 的旧固定表单这条接口不收。

`commitInfo` 按这个顺序：

1. 解析这条提交要更新的已有 KYC 主键。带了 id 就走更新，没带就准备插入。
2. 没带 id 时，同一商户、同一渠道账户上已有 `kyc_status` 为 0、2、3 的记录，就拒绝，`40022`，文案键 `kyc.pending.review`。Enhanced BIN 的新提交会跳过同渠道上普通 Visa 的待审；普通 Visa 的新提交不跳过。渠道账户对不上的待审不挡。
3. 持卡人已是拒绝、并且命中自动重提时，只重提渠道，不改 `t_merchant_kyc`，方法直接返回。没命中才继续。
4. 非 Enhanced BIN 做居住地址校验。通过只检查、不改写字段。失败抛 `40031`，文案键 `address.verification.failed`。跳过则放行。Enhanced BIN 这一步不做。地址按国籍怎么生成，见第 4 次。
5. 落库。先把这一行写成 `kyc_status = 0`，并清掉 `audit_via`。没有 id 就插入，有 id 就更新。上一行是 4 时，清掉 KYC 和该 BIN 持卡人的通知去重键。

普通 Visa 写到 0 就停。这一步不建持卡人。表单只镜像到该 BIN 上已经存在、且状态是拒绝或未激活的持卡人行。然后 `notifyKycSubmitted` 发信，模板见 `27-邮件与告警`。

Enhanced BIN 写完 0 之后跳过管理员审核，当场 `createSingleByBin`。

- 渠道调用成功，并且本地持卡人不是拒绝：改成 `kyc_status = 5`，`audit_via = 1`（平台通过），备注清空。持卡人自己仍可能是待审，等人脸结果。成功且带了核身地址时，响应 data 里有 `idvVerificationUrl`、`idvUrlExpiresAt`、`cardHolderStatus`。
- 渠道拒绝、异常或没有结果：改成 `kyc_status = 4`，`audit_via = 4`（渠道拒绝）。备注用渠道原文，没有原文就写 `System auto-processed`，最长 255。接口返回 `40405`，文案用渠道原文。
- 建人过程抛出业务异常（例如持卡人还在审核中）：异常向上抛，这一行停在刚写入的 0，不会改成 4。

其它 BIN 成功时 data 为空。

`audit_via` 只给展示。枚举：0 未标，1 平台通过，2 渠道通过，3 平台拒绝，4 渠道拒绝。门禁和查询不拿它做判断。

## 单条资料

`POST /api/v1/KYC/info`

没有请求体。登录校验和提交相同，缺登录是 `20008`。

`getLatestByMerchantId` 先取这个商户 `kyc_status = 5` 里 `create_time`、`id` 最新的一条。没有通过记录，再取任意状态里同样排序的最新一条。一条都没有时返回空 map。

有记录时，`kyc` 是这一行的字段，另补证件正面、背面、手持照的访问地址，职业代码换成展示名（`occupationValue` 保留原值），再加上 `country`、`city`、`state`。

这个接口不按 `binConfigId` 过滤。商户名下只要有一条通过，返回的就是那条通过，不会被另一个 BIN 上更新的待审盖掉。

## 记录列表

`POST /api/v1/KYC/recordList`

没有请求体。返回 `{ items: [...] }`。商户为空时是空列表。

一行对应一个 BIN，把 `t_card_holder` 和 `bin_config_id > 0` 的 `t_merchant_kyc` 合在一起。`kycStatus` 和 `merchantKycId` 取该 BIN 最新那条 KYC 原值，不走 `/info` 那种「有通过就优先通过」。这个 BIN 没有 KYC 行时，这两项从结果里拿掉。

`cardHolderStatus` 是另一套展示字符串，和数字 `kycStatus` 分开。没有持卡人时：KYC 为 0 显示待审，其它（含没有 KYC）显示未激活。有持卡人时以持卡人状态为准；持卡人已拒绝、但本 BIN 的 KYC 又是 0 时，列表仍显示待审。

## 状态

`t_merchant_kyc.kyc_status` 字段注释写着：0 用户提交，1 后台审核完成，2 待用户人脸，3 待渠道审核，4 审核不通过，5 审核通过。

这一次在写入点只看到 0、4、5。没有找到把状态写成 1、2、3 的代码。2 和 3 仍在「同渠道禁止再插入」的名单里，库里如果还留着旧行，会挡新提交。

| 现在 | 发生什么 | 变成 | 谁 |
| --- | --- | --- | --- |
| 没有可更新的行 | 普通 BIN 提交 | 0，`audit_via` 清空 | 用户 |
| 没有可更新的行，或带 id 更新 | Enhanced 提交，建人成功 | 先 0，再 5，`audit_via = 1` | 用户提交当场 |
| 同上 | Enhanced 提交，建人失败 | 先 0，再 4，`audit_via = 4` | 用户提交当场 |
| 刚写成 0 | Enhanced 建人抛业务异常 | 停在 0 | 用户提交被拦住 |
| 0 | `POST /audit/kyc/audit` 通过 | 5，`audit_via = 1`。先建持卡人，成功后再改 KYC | 管理员 |
| 0 | 同上，拒绝 | 4，`audit_via = 3` | 管理员 |
| 5 | 持卡人变成渠道通过 | 仍是 5，`audit_via` 改成 2 | 渠道回调，以及 api 里持卡人复用 |
| 5，且是 Enhanced | 持卡人变成拒绝 | 4，`audit_via = 4`。只改该商户该 BIN 最新一条 5 | UQPAY 回调 |
| 同渠道已有 0、2 或 3 | 不带 id 再提交 | 不改，`40022` | 用户被拦住 |
| 4 | 带原来的 id 再提交 | 先回到 0，Enhanced 再按建人改成 5 或 4 | 用户 |
| 5 | 商户改这一条 | 不允许更新；通过之后可以另插一条 | 用户被拦住 |

管理员审核在 `AuditKycBuServiceImpl.audit`。请求体的目标状态只接受 4 或 5，当前行必须是 0，否则 `audit.kyc.notPending`。Enhanced BIN 人工通过和人工拒绝都拒绝，文案键 `audit.kyc.enhancedCannotApprove`。没有 `binConfigId` 的旧行不能通过，拒绝仍然可以。通过或拒绝之后发信，模板见 `27-邮件与告警`。队列、权限、重复点审核归 `23-管理后台-审核`。

渠道侧只改展示和 Enhanced 的终态。持卡人变成通过时，`MerchantKycAuditViaSyncSupport` 把最新一条 `kyc_status = 5` 的 `audit_via` 写成 2，状态不动。UQPAY 回调里持卡人变成拒绝，并且 BIN 是 Enhanced 时，把最新一条 5 改成 4。已经是 4 的不再覆盖。回调验签和事件种类归 `20-渠道发卡与回调`。

`upsertApprovedFromCardHolder` 会把一行直接写成 5。注释写明只给已下线的商户站 `/cardHolder/add|edit` 用，路由删掉后这段也删。当前 `POST /submit` 不走它。审核通过后会不会自动开卡，留到 `02-用户视角` 第 2 次。

## 字段模板

`POST /api/v1/KYC/profileFields`。要登录态，商户行不存在是 `MEMBER_NOT`。body 只有 `binConfigId`。缺了在进方法前被校验拦住，文案是 “binConfigId not be null”。

`KycProfileResolverServiceImpl.resolveByBinConfigId`：商户没有 reseller 是 `BIN_CONFIG_NOT_AVAILABLE_FOR_MERCHANT`。`bin_config` 没有这行是 `BIN_CONFIG_NOT_FOUND`。这个 reseller 的 bin 控制里没有这个 BIN，也是 `BIN_CONFIG_NOT_AVAILABLE_FOR_MERCHANT`。控制表本身归 `25-分销商代理与BIN`。

解析出的 `kycProfileId` 为空或 0：`BIN_CONFIG_PROFILE_NOT_BOUND`。模板不存在：`KYC_PROFILE_NOT_FOUND`。模板 `status` 不是 1：`KYC_PROFILE_DISABLED`。通过后只取启用的字段规则。

回填用 `getForProfileFieldsBackfill`：先按 `bin_config_id` 取该商户最新一条 KYC，没有再按 `card_bin` 兜底（兼容历史上 `bin_config_id = 0` 的行）。这个 BIN 既没有 KYC 也没有持卡人时，用该商户最新一条已通过的持卡人预填，证件图再补最新一条已通过的 KYC。

响应顶层：

- `cardBin`、`kycProfileId`
- 只有 Nacos 里的 Enhanced BIN 才带 `binFlow = ENHANCED`
- `cardHolderStatus`、`rejectReason`。算法和 `recordList` 同一套
- `merchantKycId`。有值表示下次提交走更新，没有表示插入
- Enhanced 核身地址过期会先刷新，没过期才放进响应

`sections` 按规则的 `sectionKey` 分组。每段有英文 `sectionLabel`、`sectionOrder`。每个字段有 `fieldKey`、英文 `label`、`inputType`、`placeholder`、`required`、`ruleType`、`rule`、`value`、`fieldOrder`。上传字段另有 `valueUrl`。规则里没有国家名或职业名时，会在对应 id、职业代码旁边补一个只读派生字段。

## 国籍、区号、职业

`POST /api/v1/KYC/retriveProfileItems`。只要登录态，不查商户行在不在。一次返回三块：

- `countries`：`t_country.kyc_status = 1`，按 `us_name` 升序。名称用 `us_name`
- `codes`：`code_status = 1`，按区号数字升序
- `occupations`：和下面的职业列表是同一份

`POST /countryCode` 只返回上面的 `codes`。`POST /occupationList` 只返回职业。职业是写死的 7 项，每项 `{value, label}`：Education `25-9099`、Manufacturing `51-9199`、Culture and Media `27-3099`、Information Technology `15-1199`、Finance `13-2099`、Healthcare / Medical and Health `29-1199`、Other `OTHERXX`。提交存的是 `value`。历史 code 只用于回显，不出现在这个列表里。

## 持卡人详情

`POST /api/v1/KYC/cardHolder`。要登录态，商户行不存在是 `MEMBER_NOT`。body 的 BIN 可以叫 `bin`、`cardBin`、`card_bin` 或 `BIN`。空 body 或 BIN 空白时返回空对象，不报错。

按 `card_bin` 加 `merchant_id` 取 `id` 最大的一条 `t_card_holder`。没有也是空对象。有则拷贝持卡人字段，国家按 `abbr2` 查 `t_country`，三张证件照换成访问地址，职业 code 换成展示名，`occupationValue` 保留原 code。
